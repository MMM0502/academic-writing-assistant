中期项目答辩｜项目组：[填写]｜汇报人：[填写]｜日期：[填写]

开场：各位老师好，我们汇报的项目是学术文稿智能处理系统。项目聚焦论文整理中的格式规整和多篇文献综述辅助，下面介绍项目目标、系统架构、阶段成果和下一阶段计划。

## 02｜问题与项目目标（约 55 秒）

- 论文准备涉及文稿格式调整、参考文献核对和多篇文献归纳，重复劳动多。
- 手工处理容易出现引用编号不连续、文献信息缺失、正文引用与文末列表不匹配等问题。
- 项目目标：提供轻量、可本地运行的网页工具，打通单篇文稿规整和多篇文献综述两条流程。
- 定位：辅助整理与初步归纳，作者仍需核对格式、来源和学术观点。

讲述：我们不是要替代论文写作或学术判断，而是把高频、规则明确的整理步骤做成可检查的工作流。

## 03｜用户流程与核心场景（约 55 秒）

**流程 A：单篇文稿规整**  
上传 DOCX/PDF/TXT/MD → 选择 GB/T 7714、APA 7 或 IEEE → 提取文本和参考文献 → 编号规整、问题提示与引用交叉检查 → 查看并下载 Word/Markdown。

**流程 B：多篇文献综述**  
输入研究主题并批量上传 → 提取标题、年份和关键词 → 主题归组 → 生成结构化综述 → 查看并下载 Markdown。

讲述：前一条流程主要解决格式一致性和引用检查；后一条流程帮助用户从多篇材料形成初步主题脉络。

## 04｜系统架构（约 1 分 20 秒）

```text
浏览器端（HTML / CSS / JavaScript）
       │ HTTP 请求
Python 标准库 HTTP 服务与 API
       ├── 文档解析：DOCX / PDF / TXT / Markdown
       ├── 格式与引用：GB/T 7714 / APA 7 / IEEE、交叉检查
       ├── 综述引擎：本地规则与关键词聚类；可选 OpenAI-compatible API
       ├── 导出：Word / Markdown
       └── 历史记录：SQLite
```

讲述：这是一个轻量的单机架构，不依赖独立数据库服务。前端负责交互，Python 服务负责 API 和业务调度，解析、规整、综述、导出与存储拆成独立模块。大模型是可选增强项；未配置或调用失败时，系统回退本地规则引擎，核心流程仍可运行。

## 05｜关键技术与设计考虑（约 1 分钟）

- **Python 标准库 HTTP 服务**：降低安装和启动成本，适合当前 MVP 演示与本地使用。
- **HTML/CSS/JavaScript**：构成响应式网页端，直接承载上传、选择、结果查看和下载。
- **SQLite**：持久化处理历史，无需额外部署数据库。
- **规则解析与关键词聚类**：实现参考文献字段识别、格式规整和综述主题组织。
- **可选 OpenAI-compatible API**：增强文献字段识别和综述生成；失败回退本地引擎。
- **pypdf、python-docx**：可选依赖，用于更准确的 PDF 解析和 Word 导出。

讲述：选择重点是低门槛、模块清晰和可回退。格式输出由本地规则控制；大模型增强不作为系统启动的前提。

## 06｜阶段成果与验证（约 1 分 15 秒）

- 已实现浏览器首页及两条核心工作流。
- 支持四类文件输入、三种引用规范、参考文献结构化解析和编号整理。
- 支持重复文献、缺失年份、低置信度提示，以及正文引用与参考文献交叉检查。
- 支持多篇文献批量处理、关键词提取、主题分组和结构化综述生成。
- 支持 Word/Markdown 下载、SQLite 历史记录及历史删除/清空。
- 测试报告列出了单元测试、接口异常场景、下载校验和上传至下载的端到端流程。

讲述：当前形成了从上传、处理、检查到导出的完整闭环。仓库提供了测试覆盖报告；这里不报告未经现场重跑确认的通过数量。

## 07｜现场演示（约 1 分钟）

建议演示单篇规整主链路：

1. 打开首页，展示两个工作流入口。
2. 上传准备好的文稿，选择引用规范。
3. 展示参考文献信息、重复/缺失提示及正文引用检查结果。
4. 下载 Word 或 Markdown，简单展示输出。

备选：若单篇流程环境不稳定，演示多篇文献批量上传、主题分组和综述结果。演示文件应使用可公开的样例材料，不展示个人隐私或密钥。

## 08｜当前不足与风险（约 55 秒）

- 复杂 PDF、扫描件及复杂 Word 版式的解析和保留能力有限。
- 参考文献识别以规则为主，格式混杂时可能需要人工校正。
- 本地综述主要用于初步主题归纳，研究深度和观点比较能力有限。
- 外部模型能增强处理，但涉及调用稳定性、隐私和结果核验；生成内容不能替代原文证据。
- 目前仍缺少真实学生试用反馈，后续需要用实际材料检验易用性和准确性。

## 常见问题备答

**问：大模型是必需的吗？**  
答：不是。系统默认可用本地规则引擎；配置 OpenAI-compatible API 后可增强部分处理，调用失败会回退本地引擎。

**问：系统能保证生成内容准确吗？**  
答：不能替代人工核验。系统目标是辅助初步整理，用户需要对照原文确认文献信息、引用和观点。

**问：为什么不直接用复杂的前后端框架和云数据库？**  
答：当前目标是低门槛的本地 MVP，轻量架构便于安装、演示和验证核心流程；后续若有多人协作或线上部署需求，再按需求升级服务与数据层。

**问：当前最优先的改进是什么？**  
答：收集真实用户样本，优先提高复杂文档解析和参考文献识别的可靠性，并以测试和人工核验结果评估改进。
