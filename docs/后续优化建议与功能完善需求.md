# 学术文稿智能处理系统
## 后续优化建议与功能完善需求

**文档版本：** v1.0  
**适用阶段：** MVP 完成后的迭代开发与结题验收  
**产品定位：** 面向本科生、研究生和指导教师的学术文稿规整与文献综述辅助工具

## 一、文档目的

本文档用于整理当前系统存在的不足，明确后续优化方向、功能完善需求、验收标准和迭代优先级，为后续 Sprint 开发、OpenSpec 变更、测试报告和项目答辩提供依据。

本文档不改变当前 MVP 的产品定位。后续开发仍围绕两条主线展开：

1. 单篇学术文稿上传、解析、格式规整和结果导出。
2. 多篇文献上传、信息提取、研究脉络整理和综述生成。

## 二、当前版本基线

当前版本已经具备以下能力：

- 支持 DOCX、PDF、TXT 和 Markdown 文件上传。
- 支持 GB/T 7714、APA 7、IEEE 三种引用格式选择。
- 支持参考文献编号重排、疑似重复检测和年份缺失提示。
- 支持多篇文献批量上传。
- 支持关键词提取、主题分组和结构化综述生成。
- 支持本地规则引擎和可选的大模型增强模式。
- 支持 SQLite 历史记录。
- 支持 Markdown 和重新生成的 Word 文件下载。
- 已有基础网页端、单元测试、OpenSpec 文档和 CI 工作流。

当前版本更适合课程演示、内部试用和 MVP 验收。它还不能替代专业排版软件、文献管理软件或作者本人进行事实核验。

## 三、主要不足

### 3.1 文档解析能力不足

目前 DOCX 主要提取普通段落文本，PDF 主要依赖文本层解析，复杂文档的结构信息保留不完整。

具体问题：

- 无法稳定保留原 Word 的字体、字号、段落、页眉、页脚、目录和页码。
- 表格、图片、公式、脚注、尾注和批注处理能力不足。
- 扫描版 PDF、图片型 PDF 和多栏 PDF 可能无法正确提取。
- PDF 页眉、页脚、页码可能混入正文。
- 文档标题、摘要、关键词、正文和参考文献章节识别仍依赖启发式规则。

### 3.2 参考文献识别和格式化不够准确

当前实现主要依赖正则表达式和标点拆分，对规范复杂、格式混乱的参考文献支持有限。

具体问题：

- 尚未完整区分期刊、会议、学位论文、图书、网页、专利和报告等类型。
- 作者、题名、来源、年份、卷号、期号、页码、DOI 和 URL 字段提取不完整。
- 中英文混合参考文献的解析准确率需要提升。
- APA、IEEE 和 GB/T 7714 当前属于基础格式转换，不是完整标准校验器。
- 没有检查正文引用和参考文献列表是否一一对应。
- 没有提供逐条错误定位和人工确认功能。

### 3.3 Word 导出仍然是“结果重建”

当前下载的 Word 是根据处理结果重新生成的文档，不再复制原文件，但它不能完整保留原始论文的版式和图片等内容。

后续应明确区分两种导出模式：

- **规整版导出：** 使用系统重新生成规范化 Word，重点保证格式统一。
- **保留原稿导出：** 尽量保留原文档内容、图片和结构，只修改可以安全修改的格式。

### 3.4 文献综述内容较模板化

本地规则引擎当前主要依据关键词频次进行主题聚类，生成结果具有辅助性，但研究深度有限。

具体问题：

- 不能稳定提取研究问题、研究方法、数据集、实验结果和局限性。
- 不能准确比较不同文献的观点异同。
- 不能识别研究之间的继承、支持、冲突和演化关系。
- 研究不足和未来展望部分容易出现通用化表达。
- 生成内容与原文之间缺少逐句来源关联。
- 缺少用户编辑、重写、删除和重新生成能力。

### 3.5 大模型服务不够完善

当前大模型接口为可选能力，能够在失败时回退本地引擎，但还缺少完整的工程化控制。

具体问题：

- 没有明确展示当前使用的是本地引擎还是大模型。
- 缺少输入长度控制、分块处理和上下文压缩。
- 缺少调用耗时、失败原因和重试记录。
- 没有对模型输出做结构化校验。
- 没有对观点、数据和引用来源进行强制绑定。
- 缺少论文隐私、外部传输和数据删除提示。

### 3.6 前端交互能力有限

当前前端能够完成核心操作，但更接近演示界面，尚未形成完整的学术写作工作台。

缺少功能包括：

- 原文与处理结果对照查看。
- 结果在线编辑。
- 单条参考文献的修改、确认和撤销。
- 处理进度和预计等待时间提示。
- 文献列表删除、排序和重新处理。
- 结果复制、全文搜索和关键字高亮。
- Word、PDF、BibTeX、RIS、EndNote 等多种导出格式。
- 历史记录删除、重命名和再次编辑。

### 3.7 工程化和测试覆盖不足

当前系统采用 Python 标准库实现，优点是容易启动，但在正式部署和多人协作方面能力有限。

具体问题：

- `http.server` 不适合直接承担生产环境服务。
- 缺少统一 API 文档、日志、监控和错误追踪。
- 主要测试集中在解析器、格式化器、综述引擎和存储层。
- 缺少完整的接口测试、浏览器端测试和端到端测试。
- 缺少真实文档样本集和准确率评估数据。
- 缺少压力测试、并发测试和大文件测试。
- 缺少用户反馈、缺陷 Issue、PR 审阅和 Sprint 验收记录。

## 四、功能完善需求

## 4.1 P0：必须完成

P0 是影响产品可用性、核心演示和基本验收的功能，应优先完成。

### FR-P0-01 规整版 Word 导出

**需求描述：**

系统应根据处理后的正文和结构化参考文献重新生成 Word 文件，不得下载原始上传文件，也不得把未规整的参考文献段落重复写入结果。

**验收标准：**

- 下载文件扩展名为 `.docx`。
- Word 中包含规整后的标题和正文。
- Word 中只出现一次“参考文献”章节。
- 参考文献编号连续且与页面展示结果一致。
- 正文具有统一字体、字号、行距和首行缩进。
- 参考文献具有统一格式和悬挂缩进。
- 下载文件能够被 Microsoft Word 或 WPS 正常打开。

### FR-P0-02 参考文献结构化解析

**需求描述：**

系统应将参考文献拆分为作者、年份、题名、来源、卷号、期号、页码、DOI、URL 和文献类型等字段。

**验收标准：**

- 期刊论文至少能识别作者、题名、期刊、年份和页码。
- 会议论文、学位论文和网页文献能够进行类型标记。
- 无法识别的字段显示警告，不静默生成疑似错误内容。
- 页面允许用户查看每条文献的原始文本和解析结果。

### FR-P0-03 正文引用交叉检查

**需求描述：**

系统应识别正文中的数字引用和作者年份引用，并与参考文献列表进行比对。

**验收标准：**

- 能发现正文引用了但参考文献列表不存在的条目。
- 能发现参考文献列表存在但正文没有引用的条目。
- 能发现数字编号不连续或重复的问题。
- 检查结果提供具体编号或文献名称。

### FR-P0-04 核心接口和端到端测试

**需求描述：**

为上传、规整、综述生成、历史记录和下载接口补充自动化测试。

**验收标准：**

- 测试正常上传流程。
- 测试空文件、不支持格式、超大文件和损坏文件。
- 测试 Markdown 下载。
- 测试 Word 下载并验证 DOCX 压缩包结构。
- 测试历史记录写入和读取。
- 至少有一条从上传到下载的端到端测试。

### FR-P0-05 稳定的数据目录配置

**需求描述：**

默认数据库目录应使用稳定且可写的位置，并支持通过环境变量覆盖。

**验收标准：**

- 在普通用户权限下启动不会因项目目录不可写而失败。
- 支持 `DATA_DIR` 配置。
- 数据库初始化失败时显示明确错误。
- README 中给出 Windows 和 Linux 启动示例。

## 4.2 P1：核心能力提升

### FR-P1-01 保留原文内容的规整导出

系统应支持在保留图片、表格和基本章节结构的情况下，对原始 DOCX 进行可控修改。

建议先支持：

- 标题和正文样式统一。
- 段落间距和首行缩进统一。
- 参考文献段落统一。
- 页边距、页码和页眉页脚配置。

### FR-P1-02 文献分析卡片

每篇文献生成一张可编辑的信息卡片，至少包含：

- 文献标题
- 作者
- 发表年份
- 研究问题
- 研究方法
- 数据来源
- 主要结论
- 创新点
- 局限性
- 关键词
- 原文来源

### FR-P1-03 观点比较与来源追踪

综述中的关键观点应关联到来源文献。

建议输出格式：

```text
研究 A 认为……[来源：文献 1]
研究 B 则指出……[来源：文献 2]
综合来看……[来源：文献 1、文献 2]
```

系统不得把模型推测内容伪装成原文事实。

### FR-P1-04 综述编辑工作台

用户可以对生成结果进行：

- 在线编辑。
- 段落删除。
- 段落重写。
- 语气调整。
- 重新生成单个章节。
- 查看引用来源。
- 保存多个版本。

### FR-P1-05 多格式导出

除 Word 和 Markdown 外，逐步支持：

- PDF
- BibTeX
- RIS
- EndNote XML
- 纯文本

### FR-P1-06 可解释的大模型状态

页面应显示：

- 当前生成引擎。
- 是否调用外部模型。
- 处理耗时。
- 失败后是否使用本地回退。
- 数据是否发送到外部服务。

## 4.3 P2：产品扩展能力

### FR-P2-01 用户与权限

- 用户注册和登录。
- 个人工作区。
- 历史记录隔离。
- 文件和结果权限控制。
- 教师查看学生提交结果。

### FR-P2-02 在线协作

- 文稿共享。
- 评论和批注。
- 修改记录。
- 版本对比。
- 指导教师审阅。

### FR-P2-03 规范库管理

- GB/T 7714 规则库。
- APA、IEEE 等规则库。
- 学校院系自定义模板。
- 规则版本管理。
- 用户自定义引用样式。

### FR-P2-04 统计看板

- 处理文稿数量。
- 参考文献纠错数量。
- 重复文献数量。
- 用户常用引用格式。
- 综述生成耗时。
- 模型调用成功率和回退率。

## 五、非功能需求

### 5.1 可用性

- 用户无需注册即可完成 MVP 核心流程。
- 首次使用不配置大模型也能完成处理。
- 核心操作不超过三步。
- 所有异常信息使用中文，并说明下一步操作。
- 移动端页面不出现横向滚动。
- 上传、处理中、成功、失败四种状态清晰可见。

### 5.2 性能

MVP 阶段建议目标：

- 10 MB 以内 TXT 文本处理时间不超过 5 秒。
- 10 MB 以内 DOCX 文本提取时间不超过 10 秒。
- 20 页以内普通文本 PDF 处理时间不超过 20 秒。
- 10 篇以内文献的本地综述生成时间不超过 10 秒。
- 单个服务实例至少支持 5 个并发请求不崩溃。

### 5.3 安全与隐私

- 默认只监听 `127.0.0.1`。
- 单文件大小默认不超过 12 MB。
- 限制单次上传文件数量。
- 校验扩展名、MIME 类型和文件结构。
- 不执行上传文件中的脚本或宏。
- 原始文件默认只在内存中处理。
- 调用外部模型前明确提示数据传输风险。
- 支持清空历史记录。
- 生产部署必须使用 HTTPS、认证和访问控制。

### 5.4 可靠性

- 大模型调用失败时自动回退本地引擎。
- PDF 或 DOCX 解析失败时返回可读错误。
- 单个批量文献失败不能导致全部任务失败。
- 处理完成后结果必须持久化。
- 服务重启后历史记录仍可读取。

### 5.5 可维护性

- 解析、格式化、综述、导出、存储和 Web 层保持独立。
- 每个新功能必须同步更新 OpenSpec。
- 核心业务逻辑必须有单元测试。
- API 行为必须有接口测试。
- 关键用户流程必须有端到端测试。
- 每个 Sprint 保留周报、Issue、PR 和验收证据。

## 七、建议的接口完善

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/health` | 健康检查 |
| GET | `/api/history` | 获取历史记录 |
| GET | `/api/history/{id}` | 获取单条记录 |
| POST | `/api/format` | 文稿规整 |
| POST | `/api/review` | 生成文献综述 |
| GET | `/api/download/{id}?format=docx` | 下载 Word |
| GET | `/api/download/{id}?format=md` | 下载 Markdown |
| POST | `/api/check-citations` | 正文引用交叉检查 |
| DELETE | `/api/history/{id}` | 删除历史记录 |
| DELETE | `/api/history` | 清空历史记录 |
| GET | `/api/rules` | 获取引用规范列表 |

接口返回建议统一为：

```json
{
  "success": true,
  "data": {},
  "error": null,
  "request_id": "..."
}
```

## 八、推荐迭代计划

### Sprint 1：下载和规整质量

目标：让“上传论文并下载规整 Word”成为稳定完整的演示链路。

交付内容：

- 完成规整版 Word 导出。
- 完成正文和参考文献分离。
- 完成统一标题、正文和参考文献样式。
- 完成 Word 下载接口测试。
- 修复默认数据目录问题。

### Sprint 2：引用格式和交叉检查

目标：提升参考文献处理可信度。

交付内容：

- 引入结构化 Reference 模型。
- 支持期刊、会议、学位论文和网页类型。
- 增加正文引用识别。
- 增加引用与参考文献一致性检查。
- 增加错误定位和人工确认。

### Sprint 3：综述质量提升

目标：让综述从关键词拼接升级为来源可追踪的研究梳理。

交付内容：

- 生成文献分析卡片。
- 增加研究方法和主要结论字段。
- 增加观点比较。
- 增加来源标注。
- 增加综述结果编辑。

### Sprint 4：测试和工程化

目标：达到可发布和可答辩状态。

交付内容：

- 增加端到端测试。
- 增加 PDF、DOCX、批量上传测试样本。
- 完成性能测试和安全检查。
- 增加日志和统一错误处理。
- 完成 Docker 或 FastAPI 部署方案。
- 整理 Issue、PR、周报和 OpenSpec 归档。

## 十、优先级结论

建议开发顺序为：

1. 先确保下载的 Word 确实是规整结果，并且结果可打开、可核对。
2. 再完善参考文献结构化解析和正文引用交叉检查。
3. 然后提升综述的观点比较、来源追踪和在线编辑能力。
4. 最后进行 FastAPI、Docker、用户体系和协作功能等工程化扩展。

当前阶段不建议同时开发过多外围功能。对于课程项目和立项成果，最有展示价值的完整闭环是：

```text
上传论文
  -> 提取正文与参考文献
  -> 选择引用规范
  -> 发现格式问题
  -> 生成规整后的 Word
  -> 下载并核对结果
```

综述模块的展示闭环是：

```text
批量上传文献
  -> 提取标题、年份和关键词
  -> 形成主题分组
  -> 生成结构化综述
  -> 标注来源文献
  -> 在线修改并下载 Word
```

## 十一、风险说明

- 自动格式化不能保证所有复杂文献达到出版级准确率。
- 大模型生成内容必须经过作者核对，不能直接作为学术事实使用。
- 外部模型调用可能涉及论文隐私和数据合规问题。
- 规整版 Word 与原始 Word 在图片、表格和复杂样式方面可能存在差异。
- 项目最终验收前应确认课程是否允许使用本立项报告对应的系统作为实训项目。
